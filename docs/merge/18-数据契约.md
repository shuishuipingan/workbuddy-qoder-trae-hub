# 18 · 数据契约（三家引擎的字段实测）

本文只记**实测过的字段差异**，不记设计意图。所有结论都附样本量，便于复查。

> 为什么要写：第 114 轮我给账号页做"最近失败"标记，按 `account` 字段统计 —— 结果
> **trae 和 qd 的错误行里根本没有 `account`**，页面会显示"所有账号都正常"这种假绿。
> 这类错误在代码里完全合法，只有先量数据才能发现。

### 错误行

| 字段 | wb | qd | trae |
|---|---|---|---|
| `at` `iso` `model` `elapsed_ms` `error` `status` `message` | ✅ | ✅ | ✅ |
| **`account`** | **✅（多数）** | **❌** | **❌** |
| `outcome` | ✅ | ❌ | ❌ |
| `stream` `ttft_ms` `gen_ms` `msgs_sha` … | ✅ | ❌ | ❌ |

**结论**：`account` 在错误行上的存在性**因引擎而异、也因失败阶段而异**（wb 在"选完账号后失败"才带上）。
所以任何"按账号统计失败"的功能，在合并仓里必然算不全 —— 需要别的信号
（引擎的 `lastError` / 账号级 `fails` 计数）。

## 二、账号对象（`accounts/<uid>.json`）

样本：wb 28 · qd 5 · trae 2 个账号（2026-10-19 实测）

| 语义 | wb | qd | trae |
|---|---|---|---|
| 标识 | `uid` | `uid` | `uid` |
| 昵称 | `nickname` | `nickname` | ❌（用 `account`） |
| 访问凭据 | `accessToken` | `accessToken` | `token` |
| 刷新凭据 | `refreshToken` | `refreshToken` | `refresh_token` |
| 过期时间 | `expiresAt` | `expiresAt` | `expired_at` |
| 上次错误 | ❌ | `lastError` | `last_error` + `last_error_at` |
| 冷却/熔断 | ❌ | `cooldownUntil` | `cooldown_until` + `breaker_until` |
| 累计失败 | ❌ | ❌ | `fails` |
| 区域 | `realm` | `realm` | `realm` + `user_region` |
| 启停 | `enabled` | `enabled` | `enabled` |
| 权重 | `weight` | ❌ | `weight` |
| 备注 | `note` | ❌ | ❌ |

**结论**：**命名风格不统一**（wb/qd 驼峰，trae 蛇形）。融合层读账号字段必须两种都试，
否则"某一家永远显示正常"——第 114 轮就差点这样。

## 三、给写代码的人的规则

1. **不要假设字段存在**。跨引擎读字段一律 `a.x ?? a.y ?? null`，并在注释里写清两种来源。
2. **不要在错误行上做账号级归因**（除 wb 的部分情况）。要账号级健康度，用账号对象自带的字段。
3. **新增聚合端点时，把"哪些引擎可能缺这个字段"写进 docstring**（见 `hub_account_health`）。
4. **改完必须量一遍**：`python -c` 读一遍真实 jsonl 的字段集合，比看代码可靠。
5. 判据里如果引用了某个字段，注释写出**实测样本量**（本文第 1 节的写法）。

## 四、复查命令

```bash
# 看某家 usage 里成功/错误行各有哪些字段
python - <<'PY'
import json, collections
for eng, path in (("wb", "…/wb/usage/usage.jsonl"), ("trae", "…/trae2api-hub/usage/usage.jsonl")):
    ok, err = set(), set()
    for line in open(path, encoding="utf-8"):
        try: r = json.loads(line)
        except Exception: continue
        (err if (r.get("error") or (r.get("status") is not None and r.get("message") is not None)) else ok).update(r)
    print(eng, "OK:", sorted(ok))
    print(eng, "ERR:", sorted(err))
PY
```

## 五、运行时字段（磁盘注入无效）

| 引擎 | 字段 | 是否持久化 |
|---|---|---|
| wb | `lastError` `lastErrorDetail` `cooldownUntil` | **否**（`wb_accounts.py` 的 `RUNTIME_ONLY_FIELDS` 会在保存时剔除） |
| qd | `lastError` `cooldownUntil` | 是 |
| trae | `last_error` `last_error_at` `cooldown_until` `breaker_until` `fails` | 是 |

**影响**：`hub/tools/make_fixture.py` 往账号 JSON 里写 `lastError` 时，
- qd / trae：重启后能看到「最近出错」徽标；
- wb：**看不到** —— 那个字段只在进程内失败后才有值。

要验证 wb 的那条 UI 路径，只能真造一次失败（例如把某账号的 refresh token 改坏），
或者临时把 `RUNTIME_ONLY_FIELDS` 移除（不建议，那会改引擎行为）。

**冷却字段更麻烦**（2026-10-19 实测）：`cooldownUntil` 写进 qd 的账号文件后，
引擎启动时会把它**重置为 0**（文件里被改写回 0），`/accounts` 只回 `inCooldown=false`。
所以"冷却中"这个状态**没法靠夹具造出来** —— 它只由运行时真实限流触发。
要覆盖这条 UI，只能用 `_test_ui_states.js` 的 U6（直接给 render 喂数据）。

这条差异也解释了第 114 轮的一个现象：**同一个字段名，在三家的"可用性"不同。**

## 六、字段适配器（`admin/js/account-fields.js`）

三家的同一个语义经常是两个名字。适配器把这层差异**吃掉**，界面只调函数。
判据 `W89` 会扫描：`accounts.js` / `overview.js` 里**不许**再出现裸字段访问。

| 语义 | wb | qd | trae | 适配器 |
|---|---|---|---|---|
| 上次错误 | `lastError` / `lastErrorDetail` | 同 wb | `last_error` / `last_error_at` | `accountHasError` / `accountError` |
| 累计失败 | ❌ | ❌ | `fails` | `accountFails` |
| 冷却截止 | `cooldownUntil`（运行时字段） | `cooldownUntil` + `inCooldown` + `cooldownFor` | `cooldown_until` / `breaker_until` | `accountCooldownFor`（**从时间戳算**） |
| 额度 | `credits{remain,size,used}` | 同 wb（+ `plan`/`packages`） | `usage` / `entitlement`（厂商私有） | `accountQuota`（认不出 → null） |

### 三条设计规则

1. **不要读便利字段**。`inCooldown`/`cooldownFor` 只有 qd 有；读它们等于只支持一家。
   能从时间戳算的，就从时间戳算。
2. **算不出来就返回 null**，界面显示带解释的「—」。额度尤其如此：
   厂商私有结构里的数字，硬换算比不显示更危险。
3. **歧义字段不进扫描**。`credits` 在项目里有三种含义（账号额度 / 模型倍率 / 接口响应体），
   一刀切扫描只会制造误报 —— 边界写在适配器文件头部。

### 这个适配器是被咬出来的

| 轮次 | 症状 |
|---|---|
| 115 | 账号「最近出错」徽标对 trae 永不显示 |
| 120 | `healthOf()` 把 trae 的报错账号判成「正常」，筛选漏掉 |
| 121 | 概览页账号健康评分同样漏判（第四处） |
| 122 | 冷却判定只认 `inCooldown`，wb/trae 永远不显示「冷却中」 |
| 123 | trae 没有 `credits`，额度列是一个没有任何解释的「—」 |

## 七、错误体的真实形状（2026-10-19 实测）

统计三家的 `usage.jsonl` 里**判为错误**的行：

| 引擎 | 错误行 | message 是 JSON 字符串 | 占比 |
|---|---|---|---|
| wb | 260 | 46 | **18%** |
| qd | 7 | 7 | **100%** |
| trae | 无 usage 文件 | — | — |

也就是说：**错误信息不是人话，而是一段 JSON**。这带来两个后果：

1. `accounts.js` 展开错误详情时会显示 `{"code":6004,"msg":…}` —— 已由
   `humanizeError()` 还原（判据 **U18d**）；
2. `blame.js` 的归因靠**关键词匹配**，JSON 外壳理论上会干扰 —— 实测**没有**：
   260 条里没有一条落到"无法归因"，分布是 16 upstream / 29 client / 1 model（JSON 组）、
   211 upstream / 3 client（纯文本组）。判据 **U19** 用**真实行**把这条钉住（含嵌套 JSON）。

> 采样里还有个容易误判的点：wb 的 429 + `code:6004`（"usage exceeds frequency limit"）
> 归因为 **upstream** 而不是 client —— 那是上游额度限流，不是客户端乱打。
> 归因口径以 `blame.js` 为准，别照着字面猜。

### 归因与"人话"曾经自相矛盾（第 166 轮）

量 267 条真实错误，发现 qd 的 6/7 条是这样：

| 归因（改前） | 人话 |
|---|---|
| **客户端** | `isQueued=true, modelKey=cmodel, queueCount=0` |

一句话说"你的请求写错了"，另一句说"在上游排队中" —— 用户只能困惑。

原因：`errorBlame` 的规则是 **4xx 一律 client**，而 qd 把"排队"包成了 **HTTP 403**。

改法：在 4xx 分支**之前**加一条排队/并发限流规则：

```js
if (/isqueued|queued|queuecount|throttl|too many concurrent|concurrency/.test(msg)) return 'upstream';
```

分布变化：client **38 → 32**，upstream 228 → 234。判据 **U19**（7 例，含两条排队样本）。

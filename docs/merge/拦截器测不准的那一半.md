# 浏览器侧拦截器测不到的那一半（Lead 第 63 轮）

## 起因

第 60/61 轮我用一个**浏览器侧 fetch 拦截器**模拟「qd 引擎挂掉」（把 /api/qd/* 全部拦成不可达），
扫了七个页面，发现 models / logs / metrics 静默显示半个数，并逐一修好。
第 61 轮末尾我记下「rewards / accounts / settings 三页仍无提示」。

这轮去补这三页 —— **结果发现那个结论是错的。**

## 为什么错

拦掉 /api/qd/* 之后，直接打聚合端点看它报了什么：

```
GET /api/hub/rewards   →  200
{ errors: { wb: null, qd: null }, wb: {...}, qd: {...} }
                            ↑ 没有报 qd 失败
```

**因为这两种视图的取数路径根本不是同一条：**

| 视图 | 取数路径 | 浏览器拦截器能模拟引擎挂掉吗 |
|---|---|---|
| **models / logs / metrics** | 浏览器**自己**用 getBoth 打 /api/wb/* 与 /api/qd/* | ✅ **能** —— 拦掉就真挂 |
| **rewards / accounts / settings** | 调**服务端**的聚合端点 /api/hub/* | ❌ **不能** —— 聚合是服务器去 fetch 的，浏览器拦不到 |

所以对后三页来说，**那一轮跑出来的「没提示」不是缺陷** ——
它们的 qd 侧其实**一直是好的**（聚合端点返回 errors.qd = null），
页面上那个「本引擎暂无福利任务」是**真的空**，不是「取不到」。

## 教训

> **一个测试手段，只对它真正打断的那条链路有效。**
> 我拦的是浏览器的 fetch，而**有半数的视图根本不从浏览器发那个请求**。

这和之前几条是同一族：

```
「清了缓存」≠「确认了版本」
「判据在这页成立」不代表「在别的页也成立」
「模拟了故障」≠「目标链路真的断了」   ← 本轮新增
```

## 顺带确认的一件事（有价值）

**服务端聚合端点的错误上报是完整的** —— /api/hub/rewards 的形状里
errors: { wb, qd } 是**逐引擎**的，而且 aggregator.py 里确实按引擎记了原因。
也就是说：**引擎真挂时，这三页本来就有话可说** —— 只是我用错了手段，没把它试出来。

## 对判据 D22 的影响

D22（聚合体必须交代完整性）现在只覆盖 **models / metrics** 两个用 getBoth 的视图 ——
**这是对的**：桩里也是浏览器侧 fetch，所以它测的正是它该测的那条链路。
要给聚合端点那三页加同类判据，得在**服务端**造故障（例如起一个缺引擎的实例），那是另一件事。

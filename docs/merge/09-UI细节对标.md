## §1 三条先决结论（其中两条是对 Lead 审计的更正）

### 1.1 更正一：OKLCH 的技术理由**不成立** —— 而且错误来源在我们自己的代码里

Lead 说：「`oklch(from var(--accent) calc(l + 0.2) c h)` 相对色与 `color-mix(in oklch, ...)` 都要求令牌本身是 OKLCH，否则用不了」。

**【已核】MDN《Using relative colors》原文**（https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_colors/Relative_colors）：

> "relative color syntax, which allows a CSS `<color>` value to be defined **relative to another color**"

**【已核】MDN《color-mix()》原文**（https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/color-mix）：

> "takes one or more **`<color>` values** and returns the result of mixing them in a given colorspace"

⇒ 起点/输入是**任意 `<color>`**（hex、rgb、hsl 都算）。**hex 令牌照样能用相对色与 color-mix。**

**① 旧证据（token 还是 hex 时就能用）**：`admin/css/app.css:44` 写着

```css
background: color-mix(in srgb, var(--surface) 76%, transparent);
```

而当时 `--surface` 还是 hex（`#0c0f17`）—— 它一直在正常工作。

**② 更新的证据（21:52:12 起）**：令牌迁完之后，`app.css` 里出现了**正好就是注释声称「用不了」的那两个构造**，而且它们在跑：

```css
/* app.css:159 —— 注释说这个「用不了」 */
background: oklch(from var(--accent) l c h / 0.08);

/* app.css:527-528 —— 注释说这个也「用不了」 */
background: color-mix(in oklch, var(--accent) 88%, oklch(100% 0 0));
border-color: color-mix(in oklch, var(--accent) 88%, oklch(100% 0 0));
```

> 要说清楚的是：**它们现在能用，不是因为令牌变成了 OKLCH，而是因为它们本来就不挑起点。**
> 迁移的真实收益是**质量**（§1.1 那三条），不是**可用性**。
> 这个区分很重要 —— 「不能用」是个吓人的理由，会让人以为迁移是**被迫**的；实际上它是**为了更好**。

**错误的来源找到了**【实测】：`admin/css/tokens.css:22` 的注释原文就是

```text
*     ① 令牌本身不是 OKLCH → 用不了 oklch(from var(--x) …) 与 color-mix(in oklch, …)
```

**Lead 是照抄了我们自己的注释。** 所以这不只是口头转述错，是**一条错误的技术论断已经写进代码并开始传播**。

**那到底为什么还要迁到 OKLCH？**（这三条都成立，建议替换 `tokens.css:22` 那句）
1. **感知均匀** —— 同一个 L 在不同色相上观感一致，明暗层级才稳；
2. **单一颜色语法** —— 不用在 hex / rgb / oklch 三套之间心算换算；
3. `color-mix(in oklch, …)` 的混合结果符合直觉（`in srgb` 混深色会发灰）。

> 把理由改对很重要：**一个错的理由会被下一个复核的人推翻，然后连正确的规则一起被丢掉。**

### 1.2 更正二：两条被推荐的「2026 特性」**不能**当硬要求

| 特性 | 【已核】MDN 原文 | 结论 |
|---|---|---|
| `sibling-index()` | "**Baseline 2026 Newly available — Since August 2026** …This feature **might not work in older devices or browsers**." | 只能**渐进增强**（2026-08 才上线） |
| `animation-timeline` | MDN 标注**非 Baseline**："does not work in some of the most widely-used browsers" | 同上 |

（来源：https://developer.mozilla.org/en-US/docs/Web/CSS/sibling-index ・ https://developer.mozilla.org/en-US/docs/Web/CSS/animation-timeline）

**我们的现状**【实测】：`sibling-index()` 已经用了 **1** 处、`animation-timeline` **6** 处。
**这不算错**（用对了是加分），但**交付前提不能建立在它们之上** ——
内部管理台的第一要求是「打开就能用」，不是「在新版 Chrome 上很炫」。
建议：这两个特性**只在装饰性动画**上用，并且**必须有降级后的可用形态**（无动画 ≠ 无功能）。

### 1.3 更正三：组件层本来就是干净的，应该表扬

Lead 的表述「组件层全部用 OKLCH，而它们依赖的令牌层是 hex」——【实测】两半都不准：

| 文件 | `oklch(` | hex | rgb/rgba | `var(--` |
|---|---|---|---|---|
| `admin/css/app.css`（组件层） | ~~0~~ **4**（21:52:12 起） | **0** | **0** | ~~788~~ **818** |
| `admin/css/tokens.css`（令牌层，21:48 之后） | **75** | **0** | **0** | 38 |

**组件层里一个 OKLCH 都没有 —— 因为它是 788 处纯 `var(--…)` 引用，一处颜色字面量都没有。**
**这才是正确做法**：组件不碰颜色值，只引用令牌。技能里的「零硬编码 hex/rgba in components」它**本来就满分**。
真正的问题从来不是「组件层是 OKLCH」，而是「**令牌层自己没迁移完**」—— 而这条已经在 21:48 被修掉了。

### 3.1 【已核】W3C ARIA APG · Tabs —— 顶栏三档切换器的键盘契约

**来源**：https://www.w3.org/WAI/ARIA/apg/patterns/tabs/ （我读的是 "Keyboard Interaction" 与 "Examples" 两节）

**原文（逐字）**：

> "For the tab list: **Tab**: When focus moves into the tab list, places focus on the **active** tab element. …
> When focus is on a tab element in a horizontal tab list: **Left Arrow**: moves focus to the previous tab.
> If focus is on the **first** tab, moves focus to the **last** tab. … **Right Arrow**: Moves focus to the next tab.
> If focus is on the **last** tab element, moves focus to the **first** tab. … **Space or Enter**: Activates the tab
> if it was not activated automatically on focus. **Home** (Optional) … **End** (Optional) …"

还有两个**命名的**模式：
> "**Tabs With Automatic Activation**: …tabs are automatically activated and their panel is displayed when they receive focus."
> "**Tabs With Manual Activation**: …users activate a tab and display its panel by pressing Space or Enter."

**我们现在的差距**【实测】：
| 项 | 现状 |
|---|---|
| `role="tablist"` / `role="tab"` | **0 / 0** —— 现在是 `index.html:101` 的 `role="group"` + 普通按钮 |
| `aria-selected` | 3（有，这点是对的） |
| **←/→ 方向键切档** | **0** —— `ArrowLeft|ArrowRight` 在 `admin/**` 里**一次都没出现** |
| `tabindex`（roving） | **0** |
| Home / End | 无 |

**具体做法**（可直接落）：
1. 三档切换器改成 **manual activation** 的 tabs（因为切档会触发数据加载，automatic 会在按住 → 时连发请求）；
2. 容器 `role="tablist"`；每个按钮 `role="tab"` + `aria-selected` + `tabindex`（选中项 0，其余 -1）；
3. `keydown` 处理：`ArrowLeft/ArrowRight` 循环移动焦点（首↔尾绕回）、`Home/End` 到首/尾、`Space/Enter` 提交；
4. 对应面板 `role="tabpanel"` + `aria-labelledby`。

**落到哪个文件**：`admin/index.html:101`（markup）· `admin/js/app.js:729 buildEngineSwitcher()`（行为）
**谁做**：顶栏负责人（需与「三档语义化」那轮合并做，因为同一处代码）

### 3.2 【已核】W3C ARIA APG · Disclosure —— 侧栏/分组折叠

**来源**：https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/

**原文（逐字）**：
> "**Enter**: activates the disclosure control and toggles the visibility of the disclosure content.
> **Space**: activates the disclosure control and toggles the visibility … The element that shows and hides
> the content has **role button**. When the content is visible, the element with role button has

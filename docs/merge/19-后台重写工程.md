新工程**不新增颜色**，全部沿用既有 OKLCH 取值，只把它们接到 Tailwind 的 `@theme inline`：

| 旧变量 | Tailwind 工具类 | 用途 |
|---|---|---|
| `--canvas` | `bg-canvas` | 页面底 |
| `--surface` / `--surface-2` / `--overlay` | `bg-surface` / `bg-surface-2` / `bg-overlay` | 卡片 / 卡内嵌块 / 弹层 |
| `--fg` / `--fg-dim` / `--fg-mute` | `text-fg` / `text-fg-dim` / `text-fg-mute` | 三级文字 |

## 三、全局交互契约（验收会逐条查）

1. **五态齐全**：`default / hover / active / focus-visible / disabled`，每个交互元素都要有。
2. **focus-visible 必须清晰**：全局 `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px }`，**禁止 `outline: none`**。
3. **加载态**：按钮点击后 `disabled + spinner`（防重复提交）；页面数据用骨架屏，不用空白转圈。
4. **空状态**：图标 + 一句引导 + 主操作按钮，三件套。
5. **错误态**：表单错误**就地**提示（`aria-invalid` + 文案），网络错误给「重试」按钮。
6. **路由过渡**：`AnimatePresence` 淡入 180ms；`prefers-reduced-motion` 下退化为无动画。
7. **文本细节**：数字 `tabular-nums`；长文本 `truncate` / `line-clamp-2`；链接 hover 下划线动画；中英混排留白。
8. **光标**：可点击 `cursor-pointer`，禁用 `cursor-not-allowed`。
9. **滚动条**：全局细滚动条（已在 `tokens.css` 落地）。
10. **触屏**：可点目标 ≥ 44×44；hover 效果包在 `@media (hover: hover)` 内。

## 两个关键修复

1. **触屏目标**：把 `size=sm` 按钮、标签页、内联输入从 36px 提到 **44px**（`h-9 → h-11`，5 个文件 12 处），
   另外在 `tokens.css` 里加了 `@media (pointer: coarse)` 的 44px 兜底（给未来新增控件用）。
2. **开关命中区**：视觉是 44×24 的药丸，直接拉高会变形 → 用 `::after { inset: -10px 0 }` 把命中区扩到 44×44。
   实测：在开关中心**上下各 6px** 处点击仍然命中（`elementFromPoint` 确认）。

沙箱浏览器**无法模拟 `pointer: coarse`**（`Emulation.setDeviceMetricsOverride` + 触摸模拟后 `matchMedia` 仍是 `fine`）。
所以我没有拿媒体查询当验收依据 —— 而是把基线尺寸直接提到 44px，用**实测的 boundingRect** 逐个量。

### 第 34 轮（面板发布方式 + 两个严重 bug）

## 1. `Failed to fetch dynamically imported module` 的成因

不是代码问题，是**发布方式**：旧脚本「先删 admin/static 再拷 dist」，
中间几百毫秒里旧 chunk 已经 404 了。用户此时再点一个路由就报这个错。

同时把面板的自动刷新兜底从「整个会话只能刷一次」改成「15 秒内只刷一次」——
发布窗口只持续几百毫秒，但用户可能在同一标签页连撞两次。

## 2. 「两个工作区串思维链」的真凶：一个请求写了两份响应

`_merged_request()` 用 `_json()` 写完响应后**返回 None**，而调用处写的是
`if merged is not None: return merged` —— 于是它继续往下走 `_proxy()`，
**又写了一份响应**。单连接单请求看不出来（客户端只读第一份）；
keep-alive 上第二份响应会顶替下一个请求 → 后续响应整体错位一位。
表现就是：第二个窗口收到第一个窗口的回复（连思维链都串了）。

修法：`_send()` 里打 `_responded` 标记，`_dispatch()` 每请求重置，
合并分支改成 `if merged is not None or self._responded: return`。

实测（同一 keep-alive 连接连发三条，model 各不相同）：

```
修复前：A(auto)=200  B(glm-5.3)=200 但回的是 hy4  C(bogus)=200 但回的是 glm
修复后：A=200/auto   B=200/glm-5.3   C=400 upstream 400 model not exist
```

## 3. 新增判据

- **P20**：同一连接上两个请求必须拿到各自的响应（原来两条请求都缺 model，
  响应字节相同，判据形同虚设 —— 已改成两条会得到不同结果的请求）

## trae 积分“读不出来”的两个原因

**原因一：引擎侧根本没有这个字段。** v1.4.1 之前 `/accounts` 的账号视图里没有 `credits`，
面板只能退到 `/tasks.accounts[].credits`，而那个是**配额包视图**（`quota_known:false`、

### 第 39 轮（日志诊断：token=0 / 重复请求 / models 风暴）

## 1. `tokens=0 usage=missing` 是什么

引擎的 `record_usage` 只有在**收到上游 usage 块**时才记账。流式请求里 usage 是
最后一个 chunk 才带的；客户端如果在 usage 到达前断开（早退/被另一个请求顶掉），
这一段就记成 0 —— 它不是"没消耗 token"，而是"没有拿到计数"。

补强：门户在 `_proxy_stream` 里**自己解析 SSE 的 usage**，流结束时打一行
`[portal] stream done engine=wb tokens=N (in=.. out=..)`；没有 usage 就打
`tokens=? (no usage chunk: aborted or upstream omitted)` —— 一眼区分"被中断"和"上游没给"。

## 2. 每个用户回合出现两次相同请求（msgs 完全一样）

新增重复请求检测：同一份 `(model + messages)` 在 5 秒内到两次，打一条
`[portal] duplicate request fp=... model=... gap=1.8s (client sent twice?)`。
这条日志是判断"客户端双发 vs 网关重试"的唯一可靠判据 —— 之前只能猜。

## 3. `/v1/models` 每 20 秒刷 6 次

`SNAPSHOT_TTL` 从 **8s 提到 30s**：每次刷新会打 3 引擎 ×（health + 2 realm models），
8 秒一轮等于每 8 秒 9 个请求，日志被它刷屏。模型清单不是秒级数据，30s 足够。

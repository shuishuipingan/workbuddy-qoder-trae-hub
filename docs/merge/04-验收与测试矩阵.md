### 1.1 harness 的三个关键实现选择（读代码前先看这里）

| 选择 | 为什么 | 落点 |
|---|---|---|
| **影子 ESM 树**：把 `admin/js/**` 复制到 `os.tmpdir()` 下的临时目录，写一份 `{"type":"module"}` 的 package.json，再从临时目录真 import | Node 见到 `.js` 且没有 `type: module` 时按 CJS 解析，而浏览器里 `admin/js/**.js` 是原生 ESM。影子树让**源码零改动**地被真题执行（真 import 真语法），仓库里不留任何文件，跑完 `rmSync` | `admin/tests/_lib/esm.js`（`makeShadow`/`load`/`dispose`） |
| **最小 DOM 桩**：元素树 + classList/style/dataset + addEventListener/dispatchEvent + innerHTML 双通道检索 + localStorage/location/matchMedia/matchMedia 等 BOM；`fetch` 默认**抛错**（测试机不该有网），由套件按需 `setFetchImpl` 覆写 | 无浏览器也能跑 render，并且能对渲染结果做结构断言（元素数、标签数）；`fetch` 抛错保证任何「偷偷联网」会立刻暴露 | `admin/tests/_lib/dom_stub.js` |
| **超时 + 定时器清理**：编排器对每个套件设超时（默认 120 s），套件内部对每个异步步骤设 4 s 看门狗（`D STEP_TIMEOUT`），跑完 `clearAllTimers()` | 视图里一个没清掉的 `setInterval` 就足以让无头跑挂死。这条防线让「挂死」表现为一条可读的 FAIL | `admin/tests/run_all.py`、`_test_dom_render.js` |

> ⚠ **桩的完备性本身也是风险源**：无头桩不是浏览器，**桩里缺一个浏览器本来就有的 API，会把合法代码判成崩**（§4 第 6 条就是实例：`style.setProperty`）。
> 因此处理这类红的顺序是：**先判断「浏览器里成不成立」**——成立就补桩 + 加一条元层判据（`_test_selfcheck.js`），不成立才动产品。反过来做，测试就会开始扭曲产品。

### 1.2 元层反模式：测试基础设施自己制造的盲区

> 这一节的由来：两次都是**判据自己**出问题，而不是产品。共同点是——**测试基础设施把证据遮住了**。
> 它们是「元层」的失败模式：越信任判据，基础设施的盲区就越隐蔽。

### 1.3 阴性断言必须配阳性对照（柚子 07 号附录 A 提供，已按本文体例改写）

**范式**：任何「看不见」的结论（镜像里没有 X / 日志不出现 Y / 这个字段不会被写出去），都必须配一个「**去掉抑制后看得见**」的对照。
因为「当前看不到」至少有三个原因，而它们长得一模一样：

1. 抑制规则真的生效（**想要的结论**）；
2. 抑制规则写错了、而东西本来就不在（**假阴性**）；
3. 采集路径压根没覆盖（例如 `COPY` 路径根本不对）。

只有**主动把抑制去掉、让它现形**，才能把 1 与 2/3 分开。本项目范例（07 号 §3）四步缺一不可：

| 步 | 做什么 | 为什么不能省 |
|---|---|---|
| ① 正证 | 镜像内 `find` 为空 | 只有这一步 = 什么都证明不了 |
| ② 金丝雀 | 先确认宿主上 `model.json` / `state.json` **真实存在** | 没有对照物时，「镜像里没有」是句废话 |
| ③ **反证** | 掏空 `.dockerignore` 重建 → `.pyc` 0→**64**、三个金丝雀**全部出现**、体积 104→**111 MB** | 这一步才把「规则生效」和「规则写错」分开 |
| ④ 还原 | 还原后核对 `sha256` 一致 | 反证是破坏性的，必须可逆且**可验证地**可逆 |

**可直接套用的（正证 / 反证）清单**：

| 阴性结论 | 反证动作 |
|---|---|
| `.gitignore` 排除了凭据 | 临时 `git add -f` 一个假 `settings.json`，确认它**能**被加进去 |
| 日志不泄漏 token | 人为打一条带假 token 的日志，确认 `grep` **抓得到** |
| 接口需要鉴权 | 带一个**错**凭据确认返回 **401**（否则可能是根本不校验） |
| 没有外链资源 | 临时插一个外链，确认扫描器**报得出来**（本项目 `_test_selfcheck.js` A 段就是这条） |
| 测试全绿 | 故意改坏一个断言，确认 runner **变红**（本项目 `_test_selfcheck.js` C 段 / `hub/tests` 元套件） |

**建议落 CI 的三条守卫（⚠ 尚未接线）**（命令见 07 号附录 A.4）：

> 实测口径（2026-10-09 自查）：`.github/workflows/` 下**只有 `docker-publish.yml`**，里面既没有构建守卫、也没有 `tests.yml`；
> 而且**没有任何 workflow 引用 `hub/tests` 或 `admin/tests`** —— 也就是说本文这套判据目前全靠人手动跑（`python admin/tests/run_all.py`）。
> 所以下面前两条是「设计与命令已备好、线还没接」，第 ③ 条尤其危险：一旦为了过门而让构建走到无人复核的路径，阴性断言会集体假绿。① 抑制规则守卫（`.pyc` 必须 0）；② 金丝雀守卫（`accounts` 下 json 不得进镜像）；③ **阳性对照守卫**（该在的文件必须在）——第 ③ 条最容易被忽略，**没有阳性对照的阴性断言，会在「整个构建坏掉」时全部假绿**。

### 1.2.1 案例：崩溃守卫让三条「静默跳过」的判据第一次真的跑了起来（Lead 提议收录）

时间线（2026-10-09，全部可复核）：

|---|---|---|---|
| S1/S2 落点 | `(抛:HTTP [object Object])` | **判据的 bug**：探针把「api.get 抛错」当成了失败，而判据真正关心的是**请求落在哪个路径** | 改成「先记录 URL、再忽略抛错」→ 立即转绿，并确认作用域解析本身是对的 |

- ① **崩溃守卫的价值**：如果没有「套件自身不得崩」这条，上面三条会以「静默跳过」的形式长期假装通过 —— 它们不是不报错，而是**根本没跑**。判据的执行路径本身也是被测对象。

**一句话总结**：元层判据的价值来自「敢信它」；而**敢信的前提是它自己也要能被验**。所以每条元层规则都配一条自检（`_test_selfcheck.js` 的 A/B/C/E/F/G/H 段），并且基础设施的每次误报/漏报都要留下反模式记录 —— 否则下一个盲区会以同样的方式再来一次。

### 1.4 范例：判据锚点漂移时，**更新指针**而不是放宽判据

团子重写 `metrics.js` 后，能力对照套件（`_test_capability_parity.js`）**当场红**，并且直接给出新位置：

       usage-by-account: metrics.js:535 找不到「pivotCols('uid'」（现在在 :631）
       usage-by-key:     metrics.js:544 找不到「pivotCols('key'」（现在在 :640）

（注：±15 是当时的窗口，后来按 Lead 的要求放宽到 ±60 —— 但**放宽窗口并不等于放宽判据**，见下。）

③ **弱标记提示**（K6b：某字串在文件里出现多次 → 建议换更具体的字串，提示级）。
实测：漂移量表里已经能看出 `account-list 上游 -59`（离窗口边缘只剩 1 行）这类「快要漂出去」的信号。

### 1.5 错误态真实触发：四步法 + **成对断言**（阿喵提供，已在无头判据里落地）

空态与错误态是最容易「只写不验」的两种。阿喵这轮在 rewards 上跑通的四步：

```text
① 备份：copyFileSync(mock, mock + ".bak")
② 注入：目标引擎那项置 null，errors.<engine> 写成一段**可辨识文本**
③ 断言：innerText.indexOf(<那段文本>) >= 0   ← 原因真的显示出来了
         innerText.trim().length > 0          ← 不是白屏
         .statebox 数量 >= 1                  ← 走了统一状态组件
         ★ 另一侧数据仍完整                    ← 见「注意点 ②」
④ 还原：copyFileSync(bak, mock) + unlink(bak)，并复查 *.bak 残留为空
```

**注意点 ①：注入的文本必须是「只可能来自 errors」的独特串。**
阿喵第一版用了通用文案，结果**分不清是渲染成功还是兜底文案** —— 断言等于失效。能唯一定位才是断言成立的前提。

**注意点 ②：必须验证「另一个引擎仍然正常」—— 这条比四步法本身更重要。**
只测「有错误提示」会漏掉一种更严重的失败：**整个功能被整体降级**。聚合端点的 `errors` 语义是**逐引擎**的，
若实现退化成「任一侧挂就整体报错」，那么「有错误提示」照样 PASS，而健康的另一侧会跟着消失（面板从「一半可用」退成全挂）。
所以判据必须成对：**挂掉的那源显示可读原因 AND 未挂的源数据仍完整**。
推广到任意 N 源聚合视图（rewards 2 源、overview 4 源）：凡「N 个数据源合成一个视图」处，错误态都按这一对写。

**无头版落地**（`admin/tests/_test_dom_render.js` 的 **D12 系列**，注入在网络层而非改磁盘文件，所以没有 `.bak` 残留风险）：

```text
[PASS] D12a rewards wb 挂：可读原因真的显示出来了（唯一注入串）
[PASS] D12c rewards wb 挂：走了统一状态组件（.statebox 1）
[PASS] D12d ★成对断言 rewards wb 挂：未挂的 qd 侧数据仍在（13/17 个数字 token 仍在；长度 535 vs 健康 718）
[PASS] D12d ★成对断言 rewards qd 挂：未挂的 wb 侧数据仍在（12/17 个数字 token 仍在；长度 434 vs 健康 718）
```

成对断言的量化口径：**未挂侧的数字 token 至少保留 1 个**（本处 13/17、12/17）**且渲染长度 ≥ 健康态的 40%** ——
整体降级时这两个数会同时塌掉（token 归零、长度只剩一个状态盒），所以它既拦得住回归，也不会因为文案微调而误红。

### 1.7 令牌层与动效的三条硬规矩（2026 版前端标准）

> 口径来源：`modern-frontend-design`（2026）的硬规矩 + `docs/merge/06-视觉设计方向.md`。Lead 2026-10-09 实测审计后定为判据。

| 判据 | 断言 | 现状（2026-10-09） |
|---|---|---|
| **V10 零 hex/rgb** | `tokens.css` / `app.css` / `index.html` 里 `#[0-9a-f]{3,8}` 与 `rgba?(` **计数为 0**（注释除外） | 审计时 `tokens.css` 还有 **36 hex + 36 rgb()**；奶盖同轮完成 OKLCH 迁移 → **已达标（0/0）** |
| **V11 对比度地板** | 每主题：`fg`/`fg-dim`/`fg-mute` + 状态色 × 全部背景令牌，**正文 ≥4.5:1 / 图形与大字 ≥3:1** | 每主题 **36 组全过**（暗色 fg/canvas 17.95、fg-mute/canvas 5.52；亮色 fg/canvas 16.55、accent/canvas 5.37） |
| **V12 动效预算** | 只许动合成属性（`transform`/`opacity`）；`transition: all`、`transition: width/height/top/left/margin/padding…`、`@keyframes` 里 animate 布局属性 → 判红 | **4 处违例**（`app.css:149` transition height、`:366`/`:449`/`:1027` transition width）—— 进度条/配额条改 `transform: scaleX()` 即可 |
| **V12b 兜底仍在** | `prefers-reduced-motion` 兜底必须存在**且盖得住** animation/transition | 通过 |

**为什么值得做成判据**（每条都对应一个具体的失败形态）：
· V10：令牌层是 hex 时，`oklch(from var(--accent) calc(l + 0.2) c h)` 与 `color-mix(in oklch, …)` 直接报错/失效 —— 组件层已经全 OKLCH，只有令牌层会拖后腿；
· V11：**数字对、界面看不清** 是最难被功能测试发现的一类缺陷（我自己也踩过：三级文字掉到 4.5 以下），而且新加颜色令牌时没人会主动去算；
· V12：`transition: width` 会触发布局与重绘（掉帧），这类写法在进度条上极其常见、也极容易被复制到别处。

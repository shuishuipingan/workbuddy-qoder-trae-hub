# 01 · 后端融合总纲（wb 全面融入本工程）

> 决策人：Lead（小代码酱）｜依据：两轮实测（`docs/recon/*`）+ 本轮代码核对
> 目标：把 `合并damo\wb`（WorkBuddy，v1.6.17，9982 行主程序）**全面融合**进 `合并damo\qoder-proxy`（Qoder，v1.3.4）

---

## 一、先看清楚：两边本来就同构，融合是"并集"不是"移植"

| 维度 | wb（WorkBuddy） | qoder（Qoder） | 结论 |
|---|---|---|---|
| 主程序 | `wb_proxy.py` 9982 行 | `qoder_proxy.py` 7200+ 行 | 同构骨架（`Handler(BaseHTTPRequestHandler)` + 相同的函数命名族） |
| 用量账本 `usage.jsonl` | `at, iso, model, stream, elapsed_ms, ttft_ms, gen_ms, prompt_tokens, completion_tokens, reasoning_tokens, cached_tokens, total_tokens, credit, msgs_sha, n_msgs, system_sha, prefix_sha, account, realm, tokens_per_sec, cache_hit_pct` | **一字不差，21 个字段完全相同** | ✅ **直接共用一套账本** |
| 账号字段 | `uid, nickname, domain, realm, platform, accessToken, refreshToken, expiresAt, addedAt, source, enabled, lastError, cooldownUntil, credits, lastCheckin` **+ 专有**：`product, enterpriseId, proxySlot, proxy, lastDailyChat` | 上列公共 16 项 **+ 专有**：`personalToken, plan, campaignCodes, campaignBlockedUntil, userType, organizationId, organizationName` | ✅ 取**并集**即可，见 §3 |
| 出口区域 | `intl` / `cn` | `intl` / `cn` | ✅ 同构 |
| 设置 | `api_keys, panel_password_*, launcher_key, limits, pricing_*, …` | `api_keys, panel_password_*` | 取并集 + 分区 |
| 管理路由 | `/accounts /usage /realm /scheduler /settings /tasks /logs /panel/* /v1/*` | **同名冲突** | ⚠️ **必须命名空间化**，见 §2 |
| 设备指纹 | `derive_id(uid, salt)`，盐 `"machine"` / `"session"` | `derive_id(uid, salt)`，**盐串完全相同** | ⚠️ **必须分区**，见 §5 |

> 一句话：**两边是同一套架构的两个实例，融合的技术难点不在"改代码"，而在"定命名空间"。**

## 二、路由命名空间（决策 D-A）

**现状冲突**：`/accounts` `/usage` `/realm` `/scheduler` `/settings` `/tasks` `/logs` `/panel/*` `/v1/*`
两条链路上**同名**，一个进程不可能同时挂两套。

**决策：引擎路径前缀 + 共享面收敛**

```
/api/hub/...                 ← 跨引擎共享面：总览、健康、聚合用量、调度器总开关、面板会话
/api/<engine>/...            ← 单引擎面：engine ∈ {wb, qd}
    /api/wb/accounts         ← 原 /accounts
    /api/wb/usage/recent     ← 原 /usage/recent
    /api/qd/accounts
    /api/qd/usage/recent
/v1/...                      ← 推理入口保持**扁平**（客户端不想改 baseURL）
    /v1/chat/completions     → 由 API Key 绑定或模型名归属决定走哪个引擎
    /v1/models               → 两个引擎目录的**并集**（带 engine 标注）
```

**兼容别名**（一个版本周期内必须保留，避免打断已配置的客户端与旧书签）：
- 无前缀的旧路径 `/accounts`、`/usage/...`、`/settings` … → 302/内部转发到**默认引擎**（默认 `wb`，
  可用 `?engine=qd` 覆盖），并在响应头带 `X-Hub-Legacy: 1` 便于观测。
- `/panel/*`、`/health`、`/favicon.ico` 属于共享面，**不做前缀**。

## 三、账号模型并集（决策 D-B）：`schema_version: 2`

每个账号文件新增 1 个字段 `engine: "wb" | "qd"`，其余取并集（缺失字段一律 `null`，**不删字段**）：

```
公共 16：uid nickname domain realm platform accessToken refreshToken expiresAt addedAt source
        enabled lastError cooldownUntil credits lastCheckin
wb 专有 5：product enterpriseId proxySlot proxy lastDailyChat
qd 专有 7：personalToken plan campaignCodes campaignBlockedUntil userType organizationId organizationName
新增 1：  engine
```

- **存储布局**：`data/accounts/wb/<uid>.json` 与 `data/accounts/qd/<uid>.json`（物理分目录，
  避免 uid 撞车时互相覆盖；导出时仍是两个池）。
- **向后兼容**：启动时若发现旧布局（`accounts/*.json` 混放），按 `engine` 字段或文件名特征
  一次性迁移到新布局并备份原文件。

## 四、用量账本（决策 D-C）：一套账，两个引擎

- `usage.jsonl` **保持 21 字段不变**（两边已完全一致），只**追加**一个字段 `engine`。
- 位置：`data/usage/usage.jsonl`（单文件，跨引擎混写，靠 `engine` 列区分）。
- **读端不变量**：`engine` 缺失的历史行按 `null` 处理并归入"未标注"，**不得**当作 `wb` 或 `qd` 统计
  （wb 现网 21,625 行里本就有 4 行损坏、`outcome` 覆盖率 93%，读端必须容忍缺字段）。
- 四条护栏（保留积分 / 每日 Token / 每日积分 / 按模型每日 Token）的计数**按 (engine, uid) 粒度**独立，
  避免两个引擎互相占用额度。

## 五、指纹盐串分区（决策 D-D）★ 最高优先级

**风险**：`wb_fingerprint.py` 与 `qoder_fingerprint.py` 的 `derive_id(uid, salt)` 算法与盐串
（`"machine"` / `"session"`）**完全相同**。两个引擎并库后，同一个 uid 会派生出一模一样的
`machineId`，把账号的虚拟设备同时暴露给两家上游。

**决策**：盐串加**引擎命名空间前缀**，格式 `hub:<engine>:<salt>`：

```python
# hub/core/fingerprint.py
def derive_id(uid: str, salt: str, engine: str) -> str:
    seed = f"hub:{engine}:{salt}:{uid or 'anonymous'}"
    return hashlib.md5(seed.encode("utf-8")).hexdigest()[:32]
```

**⚠️ 破坏性变更声明**：改盐 = 已入池账号的 machineId 全变。必须：
1. 得到 YG 明确批准；
2. 先在**新账号**上验证不触发上游风控；
3. 保留旧算法作为 `derive_id_legacy()` 与开关 `WB_FINGERPRINT_LEGACY=1`，可一键回退。
4. 注意 `[:36]` 是恒等切片（md5 恒 32 位）——**不要"顺手修正"成 36 位**，那等于换盐。

> 备选方案（若 YG 不愿承担换盐风险）：**两套指纹模块物理隔离、各自保留原盐**，
> 只在真正共用 uid 的场景（同一个人在两个产品用同一标识）下才需要前缀区分。此方案零风险但语义不干净。

## 六、代码布局（决策 D-E）

```
qoder-proxy/
├── hub/                        ← 新增：融合层（新代码只写这里）
│   ├── __init__.py
│   ├── core/                   共享内核
│   │   ├── http.py             统一 Handler / 路由表 / 静态与 /api 分发
│   │   ├── ledger.py           用量账本（读写 + 折叠 + 缓存 + 护栏计数）
│   │   ├── accountpool.py      账号池基类（加载/持久化/亲和/轮询/冷却）
│   │   ├── fingerprint.py      derive_id 分区实现（见 §5）
│   │   └── panel.py            面板会话 / 密码 / API Key
│   ├── engines/
│   │   ├── wb/                 从 合并damo\wb 整体搬入（原样保留内部实现）
│   │   │   ├── proxy.py  accounts.py  catalog.py  pricing.py  settings.py
│   │   │   ├── tasks.py  atrest.py  webtools.py  webagent.py  scheduler.py
│   │   │   ├── identity.py  modelsdev.py  prompt.py  probes.py  ipintel.py
│   │   │   └── fingerprint.py
│   │   └── qd/                 从本工程现有 *_qoder_*.py 搬入（保持实现不变）
│   ├── aggregator.py           跨引擎聚合（模型并集、用量汇总、健康）
│   └── server.py               进程入口：起 HTTP + 调度器 + 两个引擎
├── admin/                      ← 新后台前端（本轮产出，见 00 号决策书）
├── data/                       运行时数据（gitignore）
│   ├── accounts/{wb,qd}/
│   ├── usage/usage.jsonl
│   └── settings.json
└── tests/                      两套测试并存（见 04 号）
```

**原则**：**引擎内部实现一行不改地搬进来**（降低风险），融合只发生在 `hub/core` 与 `hub/aggregator` 两层。

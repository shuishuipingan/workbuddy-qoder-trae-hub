# 17 · 三仓同步（跟上游更新）

本文回答一个问题：**上游三家各自更新了，融合仓怎么跟上？**

---

## 一、三家上游分别在哪

| 引擎 | 上游仓（默认位置） | 环境变量覆盖 | 融合仓里的位置 |
|---|---|---|---|
| wb | `Desktop/wbhub-pr`（git 镜像） | `WB_SYNC_REPO` | `hub/engines/wb/` |
| qd | `Desktop/qoder-proxy` | `QD_SYNC_REPO` | `hub/engines/qd/` |
| trae | `合并damo/trae2api-hub` | `TRAE_SYNC_REPO` | `hub/engines/trae/` |

一条命令跑完：

```bash
# 只检查，不写盘
python hub/tools/sync_upstream.py --wb --qd --trae --check

# 真同步（先 fetch + 尝试快进，再分发）
python hub/tools/sync_upstream.py --wb --qd --trae

# 只想看看会动哪些文件
python hub/tools/sync_upstream.py --trae --dry-run --force
```

## 二、每家同步哪些文件

| 引擎 | 同步集 |
|---|---|
| wb | `wb_*.py` + dashboard + pricing（见 `sync_wb`） |
| qd | `qoder_*.py` + `umid/` + dashboard + pricing（见 `sync_qd`） |
| **trae** | **`trae_*.py` + `trae_catalog_*.json` + `dashboard*.{html,js,css}` + `pricing/trae_pricing.json`** |

Trae 只有一个分发目标（`hub/engines/trae/`）——融合仓**仓根没有** Trae 文件，这与 wb/qd 不同。

## 三、融合层改过的地方：hub-patch 块

引擎文件是**原样 vendor**的，只有一处例外：看板入口会被改写成跳转到融合面。

```
# >>> hub-patch: dashboard-redirect  （改动只允许发生在这个块内）
...
# <<< hub-patch
```

判据 `S04 / S05`（引擎静态）就是在守这条：**除 hub-patch 块外，vendored 文件与上游逐字节相同**。

所以上游更新后如果判据红了，先看差在哪：
- 差在 hub-patch 块 → 正常，重新打补丁即可；
- 差在别处 → 说明同步没跑或跑了一半。

## 四、上游把补丁位置改了怎么办

`docs/merge/patches/` 下是给 wb 的补丁集。上游改了那几行的上下文，`git apply` 会失败，
这时按 `16-验证栈.md` 补记 6 的流程：**反向应用 → 重打 → 再校验**。

## 六、已知坑

1. **中文 Windows 控制台是 GBK**：工具末尾会打 ✅，不处理会抛 `UnicodeEncodeError`
   并让**成功的同步返回非零**。已在 `main()` 里 `reconfigure(errors="replace")` 兜住。
2. **trae 上游与本地可能"unrelated histories"**：`git merge --ff-only` 会拒绝。
   工具会打印警告并继续（用本地当前内容分发）；真要跟上游走，得先对齐历史。
3. **同步集按文件名前缀判定**，不是按目录：上游把文件挪进子目录仍能被抓到，
   但**改名**（如 `trae_client.py → client.py`）会让它从同步集里消失 —— 那要改 `TRAE_SYNC_GLOBS`。

## 七、出了漂移怎么办（处置手册）

先跑体检：

```bash
python hub/tools/verify_sync.py
```

它会打印每家「相同 N 个」以及两类异常：`✗ 内容不同` / `? 上游没有这个文件`。
按输出对号入座：

| 体检输出 | 含义 | 该做什么 |
|---|---|---|
| 三家全绿、`RESULT: 一致` | vendored 与上游一致（hub-patch 块内差异不计） | 什么都不用做 |
| `✗ 内容不同：xxx.py` | 融合仓里的这份被改过，或上游更新了但没同步 | 先 `git diff` 看谁改的：**融合层的改动**应该写进 hub-patch 块；**上游的更新**跑一次 `sync_upstream.py --<engine>` |
| `? 上游没有这个文件` | vendored 里有、上游没有 | 多为融合层自己加的文件（属于正常，确认后可保留）；若是引擎文件，说明上游删了它 —— 移除或补进同步集 |
| `找不到上游原件` | 那家仓不在默认位置 | 设 `WB_SYNC_REPO` / `QD_SYNC_REPO` / `TRAE_SYNC_REPO` 指向真实路径 |
| `vendored 目录里没有入口文件` | 引擎目录不完整 | 跑一次同步；仍缺就是没有 vendored 成功 |

判据侧对应关系（测试套件会同时守）：

| 判据 | 管哪一家 |
|---|---|
| `S04` | wb |
| `S05` | qd |
| `S08` | trae |
| `T08` | 体检工具本身跑得通 |

### 三种典型场景

**A. 我只是想改引擎的一行行为**
→ 不要直接改 vendored 文件。写进 `# >>> hub-patch: …` 块内，并在此文档记一条；
   否则下次同步会被覆盖，或者 S04/S05/S08 直接红。

**B. 上游发了新版本**
→ `python hub/tools/sync_upstream.py --wb --qd --trae` → 再跑 `verify_sync.py` →
   跑 `hub/tests/run_all.py`。若版本号变了，改 `hub/__init__.py` 的 `ENGINE_META`（只有一处）。

**C. 体检红了但我没动过任何东西**
→ 先看 `git -C <上游仓> log -1`：多半是上游自己更新了，而本地 vendored 还停在上个版本。

### 一句话原则

> **vendored 目录是"上游的副本 + 带标记的最小补丁"。**
> 任何不带标记的改动，都算漂移。

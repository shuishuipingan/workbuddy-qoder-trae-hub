# 假合并账（Lead 第 33 轮汇总）

> **定义**：合并态下视图读的是**作用域端点**（`get('xxx')`），而门户在合并态**不改写路径**，
> 于是请求落到**默认引擎（wb）**。表现是：页面正常、数字看着合理，**信息只覆盖一半**。
>
> 为什么危险：它不是崩溃、不是报错、也不是 0 —— 是一个**看起来完全正常的半个数**。
> 唯一可靠的发现方式是**拿两个引擎的值当面加一遍**（例如 wb 900 + qd 300 应该 = 1200）。

| # | 位置 | 合并态的错误表现 | 真值 | 修法 | 状态 |
|---|---|---|---|---|---|
| 1 | 模型清单 | 36 条（=wb） | **47 条** | 拉 4 片（wb/qd × intl/cn）后按 `engine::id` 去重 | ✅ |
| 2 | 请求流水 | 900 条（=wb） | **1200 条** | `api.getBoth` 双侧取数后按时间合并 | ✅ |
| 3 | 总览·引擎与出口 | 只显示 wb | 两个引擎 | `getBoth('health')` → 双引擎并排（各带身份色） | ✅ |
| 4 | 总览·今日用量 | 900 / 2.43 亿 / 264.22 | **1200 / 3.27 亿 / 346.88** | `/api/hub/usage` 的 `merged` 合计 + 拆分 hint | ✅ |
| 5 | 总览·账号池 KPI | 只数 wb | 并集 | `/api/hub/accounts` 的 `items` 并集 + 拆分 hint | ✅ |
| 6 | 总览·调度器 | 只显示 wb | 两个引擎 | `/api/hub/scheduler` 的 `engines` → **双栏并排**（各带自己的四时刻与模式） | ✅ |
| 7 | 数据指标 | 900（=wb） | **1200** | 两侧 analytics 的 summary 桶**只加可加量**，比率重算、均值走 sum/n | ✅ |

## ★ 真正的地基问题（第 35 轮挖到底）

上面 7 处的**共同根因**其实不是每个视图写错了 —— 而是 api.getBoth() **一直是坏的**：

```js
// 第 22 轮我把令牌存储从 sessionStorage 换到 localStorage，
// 但 getBoth 里读槽的代码仍然写死 sessionStorage：
try { tok = sessionStorage.getItem(slot); } catch (_) {}   // ← 恒为 null
```

于是 getBoth **永远不加 per-engine 头** → 请求退回默认槽 → **qd 那一侧恒 401**
→ 静默返回 {wb: 有, qd: null, errors:{qd:'unauthorized'}}。

**症状和假合并一模一样**（模型 36 / 流水 900 / 指标 900），我按假合并查了两轮才挖到它。
换存储介质时**所有读它的地方都要一起换** —— 漏一处就变成一个看起来是别的问题的问题。

修好之后，**无需改任何视图**：模型清单自动从 36 变 47、请求流水从 900 变 1200。

## 三条合并口径（都是踩出来的）

| 数据种类 | 正确做法 | 错的会怎样 |
|---|---|---|
| **计数**（requests / tokens / credit） | 相加 | — |
| **比率**（命中率 / 推理占比） | **用合计重算** | 实测出现 **193.4% 和 102.7%** —— 超过 100% |
| **均值**（延迟 / 速度） | 合计 sum ÷ 合计 n | 简单相加出现 **15.4 s**（真值 7.71 s） |

**「百分比超过 100%」是这类错误唯一显眼的地方** —— 而且它当场就在屏幕上。

## 两条必须遵守的规矩（都是踩出来的）

1. **render 与 update 必须同口径**。只改 render 不改 update，结果是**刷新一次就退回"只有 wb"** ——
   界面在"合并"和"只有 wb"之间来回跳，比一直只显示 wb 更难查。
2. **出处要写在界面上**。用量给「合计 + 拆分」而不是只给合计，也不是并排两组：
   用量是**可加量**，合计让人看懂"一共多少"、拆分让人看清"谁贡献的"。
   而引擎的出口/版本/凭据**不可加**，必须并排两块（合成一份会让人以为"改一处影响两边"）。
